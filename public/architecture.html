01 The big idea

The agent's harness is a database.

Most LLM agents hide their memory and control flow in a JavaScript object or a server. Tables does the opposite: the entire agent — its memory, its tool calls, its dashboards, and the loop that drives it — lives inside an in-browser SQLite database. You can SELECT * FROM messages and read the agent's whole mind.

nicklisac/tables on GitHub

The ReAct loop is not a while loop in JavaScript. It is a cascade of SQLite triggers. Drop a user message into messages and the database reacts to itself — thinking, acting, observing — until it stops. The only JavaScript that runs is the thin layer that does browser I/O and network requests. Everything else is declarative SQL living in the database.

04 Time travel

      
Rewind the data. Compact the memory.

      

        Two independent systems give the agent a sense of time — one for undoing what it
        did to your data, one for forgetting what it no longer needs in context.
      


      

        

          
⟲ Rewind — undo a turn

          

            Every turn runs inside an atomic SAVEPOINT turn_sp. Per-table
            capture triggers (cap_*) write a pre/post row
            image for every change into turn_changesets; DDL goes to
            turn_ddl_log with a pre-image. Click the
            ⟲ on any message and the inverse is replayed — data and schema
            return to that turn, while the conversation is kept. A 20-turn ring buffer bounds the cost.
          

          

            
          

        


        

          
◐ Compact — shrink the context

          

            When token usage nears the model's window, the oldest turns are summarized into a
            compactions row and a watermark advances.
            The v_active_context view simply stops reading rows below the
            watermark. The messages table is never touched —
            it stays a complete, immutable audit log.
          

          

            
          

        

      

    


    
    

      
05 The boundary

      
The agent can't break its own harness.

      

        A powerful agent that can run arbitrary SQL could also DROP TABLE
        messages and destroy itself. Tables draws a hard line: the app's own tables are
        protected from destructive DDL, so the agent can analyze your data without ever
        corrupting the machinery that runs it.

06 The stack

      
Why this is even possible: JSPI.

      

        The crux of the whole design is a single capability: a SQL function that can wait on the
        network and then resume. That's what JavaScript Promise Integration (JSPI) adds to
        WebAssembly — and it's what lets an LLM call happen inside a trigger.
      


      

        

          1
          Browser JS
          DOM, file I/O, the network — the only imperative layer
        

        

          2
          JSPI fibers
          suspend a WASM call on a promise, resume when it settles
        

        

          3
          SQLite (WASM)
          the engine — tables, views, triggers, UDFs
        

        

          4
          The harness
          agent_think · execute_tool · ask_llm · capture triggers
        

      


      

        

          When agent_think calls the
          ask_llm UDF, the UDF makes an HTTP request to your LLM provider.
          Without JSPI, the WASM module would block the whole browser thread. With JSPI, the fiber
          pauses — the trigger is genuinely suspended mid-statement — and the browser is
          free to render, stream tokens, and handle clicks. When the LLM's JSON arrives, the fiber
          resumes and the trigger continues, inserting the assistant row and re-triggering
          the cascade.
        

        
-- inside the agent_think trigger, this one call suspends the whole WASM fiber:
SELECT ask_llm(
    (SELECT json_group_array(json_object(...)) FROM v_active_context),
    (SELECT json_group_array(json(schema)) FROM tools)
) AS llm_response;  -- ⏸ fiber parks here while the network round-trip happens
